# Reading the Kordi calendar in chat

Ordinary desktop and cloud fallback chat expose the read-only `read_calendar` tool. It reads saved Kordi calendar events through the authenticated calendar store, preserving source visibility checks. It does not read external calendar services directly and does not promote chat arrangements or digest proposals into saved events.

The tool accepts optional `startAt` and `endAt` RFC3339 bounds and an `offset`. Results contain at most 50 event summaries, an account timezone when configured, and `hasMore` / `nextOffset` for pagination. Timed events overlap the requested interval; all-day events retain calendar-date semantics. `status: empty` means no saved events match the window, whereas `status: ready` with an empty page means the offset is beyond the matching events. Retrieval failures never mean the calendar is empty.

The host binds the account and conversation; model arguments cannot choose them. Desktop reads use the signed-in account and authenticated turn identity. Cloud reads use a live runner lease and the admitted run owner/requester. An Agent only ever reads its own owner's calendar: nobody reads another person's calendar directly, and another person's agent can only ask the owner's Agent. Cloud execution subsessions, child runs, and System agent runs cannot use this capability.

In a shared conversation the disclosure level depends on who asked. Every shared read revalidates the request on the server: a current, visible, human-authored message (or an agent exchange that started from one) and active membership. Quoted text, agent-authored messages, and System messages never grant access.

- **The owner's own request: availability by default.** When the owner's request needs their availability (planning, scheduling, finding a time), the Agent reads the calendar without asking first. The server returns `disclosure: "availability"` and `busyWindows` with only `startAt`, `endAt`, `allDay`, `timezone`, and `busy`. Titles, descriptions, links, sources, event IDs, series, and revisions are stripped on the server, not only by the prompt. The Agent shares only the free or busy times relevant to the request.
- **The owner's own request: details.** Event summaries in a shared conversation still require `shareInConversation: true`, which the tool instructions permit only when the owner explicitly asks to read or share their calendar events in that conversation. A request with `disclosure: "details"` but without that flag is rejected.
- **Another member, or their agent, asks the owner's Agent: availability only.** This covers another member's direct request to the owner's Agent and an agent exchange in which another member's agent asked the owner's Agent (`agent-exchange:<id>:request`). The server requires the original human request, the requester, and the asking agent's owner to be active members, and the owner's "Share busy/free with people in my chats" setting to be on (`shareCalendarAvailability` on `GET/PATCH /v1/cloud/auth/me`, stored in `cloud_accounts.share_calendar_availability`, default on). Any request for details on someone else's behalf (`shareInConversation` or `disclosure: "details"`) is rejected; the desktop tool and the cloud runner refuse it before calling the server. The response scope is `member_requested_shared_availability`.

Clients send `disclosure: "availability"` for shared reads without `shareInConversation`; the server applies the same default when the field is absent. When an Agent run continues after another agent replied (`agent-exchange:<id>:resume`), the server resolves it to the original human request and allows availability only, under the same rules as that request. Cloud context reads also require the request's sender to be the admitted run's requester. Private chats with the owner's own Agent are unchanged and return details. Responses never include source IDs, descriptions, links, or reminder metadata, and the Agent must summarize only the requested dates and details.

Desktop calls `POST /v1/cloud/calendar/read`; cloud fallback dispatches through the run-authorized context endpoint. Both use the same calendar reader. Regression coverage lives in the tools calendar tests, desktop calendar runtime tests, cloud model-loop tests, and the calendar HTTP integration test. The HTTP test requires a fresh isolated PostgreSQL database containing synthetic fixtures only.
