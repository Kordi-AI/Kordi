# Reading the Kordi calendar in chat

Ordinary desktop and cloud fallback chat expose the read-only `read_calendar` tool. It reads saved Kordi calendar events through the authenticated calendar store, preserving source visibility checks. It does not read external calendar services directly and does not promote chat arrangements or digest proposals into saved events.

The tool accepts optional `startAt` and `endAt` RFC3339 bounds and an `offset`. Results contain at most 50 event summaries, an account timezone when configured, and `hasMore` / `nextOffset` for pagination. Timed events overlap the requested interval; all-day events retain calendar-date semantics. `status: empty` means no saved events match the window, whereas `status: ready` with an empty page means the offset is beyond the matching events. Retrieval failures never mean the calendar is empty.

The host binds the account and conversation; model arguments cannot choose them. Desktop reads use the signed-in account and authenticated turn identity. Cloud reads use a live runner lease and the admitted run owner/requester. Requests addressed to another person's Agent cannot read that person's private calendar. Cloud execution subsessions cannot use this capability.

In a shared conversation the disclosure level depends on what the owner asked for. The server requires a current, visible, owner-authored human request and active membership for every shared read; mentions, agent handoffs, quoted text, and another participant's requests never grant access.

- **Availability (default).** When the owner's own request needs their availability (planning, scheduling, finding a time), the Agent reads the calendar without asking first. The server returns `disclosure: "availability"` and `busyWindows` with only `startAt`, `endAt`, `allDay`, `timezone`, and `busy`. Titles, descriptions, links, sources, event IDs, series, and revisions are stripped on the server, not only by the prompt. The Agent shares only the free or busy times relevant to the request.
- **Details.** Event summaries in a shared conversation still require `shareInConversation: true`, which the tool instructions permit only when the owner explicitly asks to read or share their calendar events in that conversation. A request with `disclosure: "details"` but without that flag is rejected.

Clients send `disclosure: "availability"` for shared reads without `shareInConversation`; the server applies the same default when the field is absent. When an owner-requested run continues after another agent replied (an `agent-exchange:<id>:resume` request), the server resolves it to the original human request and allows availability only. Requests another agent sent to the owner's agents (`agent-exchange:<id>:request`), runs requested by someone other than the owner, and execution subsessions never read the calendar. Private chats with the owner's own Agent are unchanged and return details. Responses never include source IDs, descriptions, links, or reminder metadata, and the Agent must summarize only the requested dates and details.

Desktop calls `POST /v1/cloud/calendar/read`; cloud fallback dispatches through the run-authorized context endpoint. Both use the same calendar reader. Regression coverage lives in the tools calendar tests, desktop calendar runtime tests, cloud model-loop tests, and the calendar HTTP integration test. The HTTP test requires a fresh isolated PostgreSQL database containing synthetic fixtures only.
